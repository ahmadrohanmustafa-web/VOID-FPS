# Minecraft 26.3 native block-render pipeline

## Evidence source

This note is based on the Minecraft 26.3 client bytecode and signatures produced by the successful Build #224 inspection artifact (commit `4126bb33eee135931611bd5c32431071c69560f1`). It records observed control flow, not a verified mixin target or permission to replace vanilla rendering.

## Observed section-compilation flow

1. `SectionCompiler.compile(...)` creates the section result and visibility graph, then calls `BlockModelLighter.enableCaching()`.
2. It constructs a `ModelBlockRenderer` using the section compiler's ambient-occlusion setting, culling enabled, and the registered `BlockColors`.
3. It creates two `BlockQuadOutput` callbacks. The inspected callback bodies route quads to `BufferBuilder.putBlockBakedQuad(...)`; one selects the layer from each quad's `MaterialInfo`, while the other routes to `ChunkSectionLayer.SOLID`.
4. The section loop visits the 16×16×16 block positions. It skips air, updates the visibility graph for solid-render states, collects block entities, and tessellates non-empty fluids separately.
5. For states with `RenderShape.MODEL`, it chooses an output callback, obtains the native `BlockStateModel` from `BlockStateModelSet`, computes the block's position-dependent seed, and calls `ModelBlockRenderer.tesselateBlock(...)`.
6. `ModelBlockRenderer` selects model parts with the supplied seed, visits directional and unculled quads, applies native face-culling checks, prepares either ambient-occlusion or flat lighting through `BlockModelLighter`, applies tint where the material has a tint index, then calls `BlockQuadOutput.put(...)`.
7. The output callback passes the baked quad and prepared `QuadInstance` to `BufferBuilder.putBlockBakedQuad(...)`. The native vertex consumer writes positions, packed color, UV, overlay, light (including material emission), and normal.

## Consequences for VOID FPS

- A block-only replacement must not bypass the section compiler's fluid path or block-entity collection.
- Model part selection must use the same position seed and native model selection behavior.
- Directional and unculled quads must retain their native ordering and semantics.
- Culling must remain equivalent to `ModelBlockRenderer.shouldRenderFace`, which delegates to `Block.shouldRenderFace`; Minecraft already caches face-occlusion checks.
- AO/flat lighting and tint are prepared before the output callback. A candidate that changes either must be compared at the prepared-quad boundary, not inferred from geometry alone.
- The final packed vertex path includes material light emission. Matching only positions and UVs is insufficient.
- The two output callbacks have different layer-routing behavior. A candidate must preserve the selected output/layer.

## Next verification milestone

Build a **test-only capture seam** around the native `BlockQuadOutput.put(...)` boundary, or an equally faithful test harness, and record the actual vanilla prepared quads for a controlled block fixture. Compare ordered records containing:

- block-relative translation and all four vertex positions;
- native quad direction and material/layer metadata;
- all four colors and packed UV pairs;
- overlay coordinates and packed light after material emission;
- all four normals;
- output layer and quad ordering.

The capture must come from the real `ModelBlockRenderer.tesselateBlock(...)` path with a real section-region/world fixture. The existing synthetic `VertexConsumer` test validates the packing contract only; it is not a vanilla-versus-candidate rendering parity test.

## Activation gate

Do not add a production mixin or activate custom rendering until the capture seam proves exact parity for supported fixtures, fallback behavior is verified for unsupported blocks, visual equivalence is checked, and repeatable before/after benchmarks show a benefit. Until then the production entrypoint must continue to leave block and terrain rendering untouched.
